# Learning orderflow

This is a walkthrough for someone who already knows processes, transactions, and networks, and has not written Java or used Spring. Read it next to the code. Every decision below names the file that makes it real, then the question an interviewer is likely to ask and a short answer.

Java syntax you need for this repo: a `record` is an immutable data holder with generated accessors. An `interface` is a contract. A class marked `@Component` or `@Service` is created by Spring and passed into other constructors. That constructor injection is the whole dependency mechanism. `@Transactional` means "run this method in a database transaction, and roll it back if a runtime exception escapes."

## Why these are separate services

An order, a stock count, and a payment decision change on different clocks. Stock must be correct when someone else is buying the same SKU. Payment can take seconds and can say no. The read API is allowed to be a few hundred milliseconds behind, and it must not store the payment token.

Putting those in one process would make the demo smaller. It would also hide the problems this design is here to show: a call that fails halfway, an event that is delivered twice, and a read model that has not caught up.

The split is:

- `order-service` owns the order row and the saga. Postgres database `orders`.
- `inventory-service` owns available and reserved counts. Postgres database `inventory`. gRPC on port 9090, HTTP on 8082 for the stock read.
- `payment-service` owns the charge record. Postgres database `payment`.
- `query-service` owns the MongoDB document a client can browse.
- `api-gateway` is Spring Cloud Gateway. It does not own data. Routes are in `api-gateway/src/main/resources/application.yml`.

They do not share a schema. `docker/postgres/init.sql` creates three databases on one server so a laptop can boot the system. That is a deployment shortcut, not a shared-database design.

**Follow-up: why not one database with three schemas?**
Schemas would still let a transaction touch stock and the order together, which hides the failure mode. Separate databases make a cross-service transaction impossible, so the saga has to be explicit.

**Follow-up: what do you lose?**
A single SQL join across order and stock. You replace it with an API call or an event. You also operate four deployables. For a portfolio that is the point. For a three-person team shipping one product, a modular monolith is often the better first step, and you can still keep these package boundaries.

## REST at the edge, gRPC between order and inventory

The public API is HTTP because that is what `curl`, browsers, and API gateways already speak. Order routes are `OrderController` (`order-service/src/main/java/com/orderflow/order/api/OrderController.java`). OpenAPI is generated by springdoc on each service at `/swagger-ui.html`. The contract for stock is `orderflow-proto/src/main/proto/inventory.proto`, compiled into `com.orderflow.inventory.v1`.

`PlaceOrderService` calls inventory while the HTTP request is still open. The caller needs a yes or a no before it can tell the client the order is waiting for payment. gRPC gives a small binary contract and a deadline (`orderflow.inventory.deadline` in `order-service/src/main/resources/application.yml`). The client is `InventoryGrpcAdapter`.

Payment is not on that path. Charging can be slow, and the result must survive a restart, so payment is `ORDER_PAYMENT_REQUESTED` on Kafka topic `order.events` (`com.orderflow.common.Topics`). The query API is GraphQL because the client asks for a shape, not because GraphQL is better than REST. The schema is `query-service/src/main/resources/graphql/order.graphqls` and the fetch is `OrderGraphqlController`.

**Follow-up: why not gRPC from the gateway too?**
The gateway would grow a second public protocol, and every sample client would need generated stubs. HTTP at the boundary keeps the demo usable. gRPC is justified where both sides are our processes and the call is synchronous.

**Follow-up: why not REST for the reserve call?**
REST would work. gRPC is here because the call is internal, the payload is a closed set of fields, and a deadline plus status codes map cleanly onto retry policy. The interesting part is not the bytes. It is that business failures and transport failures are different, which `InventoryGrpcAdapter` encodes: `FAILED_PRECONDITION` becomes `ReservationAttempt.Rejected`, and `UNAVAILABLE` or a timeout becomes `InventoryTemporarilyUnavailableException`.

## The outbox

After the order is saved, something has to tell payment. Writing the row and then publishing to Kafka is two operations. If the process dies after the commit and before the publish, payment never hears about the order. If you publish before the commit and the commit fails, payment charges an order that does not exist.

`OrderTransaction.create` and `applyReservation` save the order and call `DomainEventPublisher` in the same `@Transactional` method. `OutboxRecordingObserver` (`order-service/src/main/java/com/orderflow/order/infrastructure/observer/OutboxRecordingObserver.java`) inserts the JSON into `outbox_events` in that same transaction. `OutboxRelay` polls unpublished rows, sends them, and marks them published.

The mark happens after the send. A crash in between publishes the event twice. That is acceptable because every consumer dedupes. It is not acceptable to lose the event.

Payment has the same shape in `payment-service/src/main/java/com/orderflow/payment/infrastructure/messaging/OutboxRelay.java`. The repository methods that mark a row are `@Transactional`. A `@Modifying` query outside a transaction throws, the row stays unpublished, and every later event in that poll waits behind it. The saga test caught that.

**Follow-up: why poll instead of reading the Postgres WAL?**
A poller is a few dozen lines and a scheduled method. Debezium or a logical-replication publisher tails the log and does not add a poll delay. It also adds a connector to operate. At this size the poll interval (400 ms by default) is the right trade. At higher volume you want the log tail, so the database does the capture instead of a `SELECT` every few hundred milliseconds.

**Follow-up: what orders the events?**
The relay stops the batch on the first send failure, so one order's events stay in `created_at` order while Kafka is down. Kafka then preserves order per partition, and the key is the aggregate id. Two different orders can still be applied out of order on the query side. The version check covers that.

## Saga instead of two-phase commit

Two-phase commit would ask inventory and payment to prepare, then commit both. Payment's decision can take long enough that you do not want a stock row locked the whole time. If the coordinator dies after one participant commits, you have a heuristic outcome that an operator has to repair. 2PC also requires every store to speak the same transaction protocol. MongoDB in this design does not.

The saga is local transactions plus a compensating action:

1. Insert the order as `PLACED` with `ORDER_PLACED`. No remote call inside the transaction. See `OrderTransaction.create`.
2. Reserve stock. On a definite no, `applyReservation` moves the order to `REJECTED` and the HTTP status is 409.
3. On a yes, move to `PAYMENT_PENDING` and emit `ORDER_PAYMENT_REQUESTED`, which carries the token.
4. `PaymentProcessor` charges and emits `PAYMENT_AUTHORIZED` or `PAYMENT_DECLINED`.
5. `PaymentResultHandler` confirms, or calls `release` and `finishCompensation`.

`SagaRecoveryJob` covers the holes. An order left in `PLACED` because inventory timed out is reserved again. The reserve is idempotent on order id, so the second call does not take two units. An order left in `PAYMENT_PENDING` past `orderflow.saga.payment-timeout-ms` (10 minutes) is compensated. An order stuck in `COMPENSATING` gets another release.

**Follow-up: what if the card is approved after you already released the stock?**
`OrderTransaction.onPaymentAuthorized` confirms only from `PAYMENT_PENDING`. Any other status is logged and the inbox records the event. There is no refund workflow. Say that plainly. A production saga would open a refund, which is itself another compensatable step, and it would keep the authorization id.

**Follow-up: orchestration or choreography?**
This is orchestration sitting inside the order service. The order service decides to reserve, to request payment, and to release. Payment does not know the order lifecycle. Choreography would let payment and inventory each react without a coordinator. That spreads the policy. Here the policy is the interesting part, so one class (`PlaceOrderService`, `PaymentResultHandler`, `SagaRecoveryJob`) owns it.

## Postgres, MongoDB, and what "consistent" means

Command tables need a transaction that can roll back a half-applied reservation. `InventoryReservationService` locks SKUs in sorted order, decrements `available`, increments `reserved`, and inserts the reservation. A shortage throws, and the transaction undoes the earlier lines. The constraints live in `inventory-service/src/main/resources/db/migration/inventory/V1__init.sql`. JPA is set to `ddl-auto: validate`, so Hibernate checks the mapping and Flyway owns the schema.

The query side stores one document in `order_views`. `OrderProjection.apply` ignores an event whose `aggregateVersion` is not newer than the document, and it never copies `paymentToken`. MongoDB is running standalone here, so there is no multi-document transaction. The version check is what makes a replay and a reorder safe without one.

The consistency model is:

- Inside one Postgres database, a transaction is atomic.
- Across services, the system is eventually consistent. `POST` can return `PAYMENT_PENDING` before GraphQL shows that status.
- Reads of the write model (`GET /api/orders/{id}`) are read-your-write for that order, because they hit the same row the command just committed.
- Reads of GraphQL are not.

**Follow-up: why not Cassandra?**
Cassandra would fit a high-write event log or a time-series of stock movements. The order aggregate is a small row that you update in place under a lock. That is Postgres. The read model is one document looked up by id or customer. That is MongoDB. Cassandra would make the lock and the conditional update harder without buying anything this demo needs.

**Follow-up: can the read model go backwards?**
Not if every event carries a full snapshot and a monotonic `aggregateVersion`. An older snapshot is dropped. A gap is fine: version 3 replaces version 1 without applying version 2, because the snapshot is complete. That is why the payload is an `OrderSnapshot` and not a tiny delta. The cost is a bigger message.

## Idempotency

Retries happen at four layers, and each one has its own key.

| Retry | Key | Where |
| --- | --- | --- |
| Client repeats POST | `Idempotency-Key` plus a SHA-256 of the body | `PlaceOrderService`, table `idempotency_keys` |
| Order service retries reserve | order id | `InventoryReservationService` |
| Kafka redelivers a payment request | event id inbox, and unique `payments.order_id` | `PaymentProcessor` |
| Kafka redelivers a payment result | event id in `processed_events` | `OrderTransaction` |
| Query sees a duplicate or an old snapshot | event id, then aggregate version | `OrderProjection` |

The HTTP rule is in `PlaceOrderService.place`. A reused key with the same hash returns the stored order and does not reserve again. A reused key with a different hash throws `IdempotencyConflictException`, which the controller turns into 409. The hash is the canonical body, not the raw bytes, so whitespace does not matter and a changed token does.

Inventory: an `ACTIVE` reservation for that order id returns the original reservation id. A `RELEASED` one throws, so a compensated order cannot reserve a second time by accident.

Payment: `publishResult` uses a deterministic event id derived from the payment id, so a reprocessed request does not invent a second result. The inbox insert is `ON CONFLICT DO NOTHING`.

**Follow-up: is the HTTP key enough?**
No. The client key protects the client. Kafka will redeliver even when the client only called once. The inbox is what protects the saga. Skipping either one leaves a hole.

**Follow-up: what if two requests with the same key pass the read at the same time?**
The unique primary key on `idempotency_keys` makes one insert fail. `PlaceOrderService` catches `DataIntegrityViolationException` outside the transaction and replays the winner. Catching it inside the transaction would mark that transaction rollback-only, and the replay would never commit.

## The patterns, and why each one is here

A pattern earns a place when removing it would scatter a rule. These would.

### State

`OrderStatus` is the stored name. The behavior is `OrderState` in `order-service/src/main/java/com/orderflow/order/domain/state/`. `PlacedState` can request payment or reject. `PaymentPendingState` can confirm or start compensation. `CompensatingState` can finish cancellation. The terminal states throw `IllegalOrderTransitionException` for every action. `Order` calls the state object and then records the event. `OrderStateFactory` picks the object from the enum when a row is loaded.

The rule "you cannot confirm a cancelled order" lives in one method instead of an `if` in every application service.

**Follow-up: why not a switch in the aggregate?**
A switch works at this size. The state objects make the illegal edges the default, so a new status does not silently inherit a transition. The factory is the only switch, and it is exhaustive over the enum.

### Strategy

`PaymentStrategy` has one method, `charge`. `CardPaymentStrategy` declines a blank token and any token that ends in `0002`. `WalletPaymentStrategy` declines an amount above `50_000` minor units. `PaymentStrategyFactory` (`payment-service/src/main/java/com/orderflow/payment/domain/PaymentStrategyFactory.java`) maps the method enum to the strategy. `PaymentProcessor` does not contain those rules.

**Follow-up: why a factory and not a Spring map injected straight into the processor?**
The factory is the place that turns "no strategy registered" into a single error. The processor then declines an unknown method instead of throwing, which would make Kafka retry the record forever. The policy for a missing strategy is a decision, so it has a type.

### Factory

Two factories, both because a caller should not `new` the variant:

- `OrderStateFactory.from` rebuilds the behavior for a status loaded from a row.
- `PaymentStrategyFactory.forMethod` selects the charge algorithm.

Neither one constructs a complicated object graph. The Builder does that. The factories select a behavior. That is the distinction worth making out loud.

### Builder

`Order.Builder` is the inner class at the bottom of `order-service/src/main/java/com/orderflow/order/domain/Order.java`. It requires an id, customer, currency, lines, clock reading, correlation id, and the state factory. It sums the lines with `Money`, rejects a currency mismatch, and records `ORDER_PLACED` with the token omitted. `rehydrate` is the other constructor path, used when a row is loaded, and it records nothing.

**Follow-up: why not a constructor with fourteen arguments?**
The constructor exists and is private. The builder names the arguments at the call site and is the only path that emits the placement event. Persistence must not emit that event again, so it uses `rehydrate`.

### Observer

`Order` collects `OrderDomainEvent`s. `DomainEventPublisher` hands them to every `DomainEventObserver`. Two observers ship with the service:

- `OutboxRecordingObserver` writes the integration event.
- `OrderMetricsObserver` increments `orderflow.order.events`.

The aggregate does not know about Kafka or Micrometer. Adding a third reaction does not change `Order`.

**Follow-up: how is this different from Spring's `ApplicationEventPublisher`?**
Spring's publisher is the same idea at the framework boundary, and it is tied to the Spring context. This publisher is a plain list of observers so the domain test can run without a context. The transaction still surrounds the call, which is what makes the outbox atomic with the order.

### Adapter

Ports are the interfaces in `order-service/src/main/java/com/orderflow/order/domain/port/`. Adapters implement them:

- `InventoryGrpcAdapter` speaks gRPC and Resilience4j. The domain sees `ReservationAttempt`.
- `OrderRepositoryAdapter`, `OutboxStoreAdapter`, `InboxStoreAdapter`, and `IdempotencyStoreAdapter` speak JPA.

The gRPC messages and the entity classes do not leak into `Order` or `PlaceOrderService`. That is the whole point of the adapter. A test can pass a fake `InventoryReservationPort`, which `OrderOutboxIntegrationTest` does, and the outbox behavior is still real.

### Chain of Responsibility, with a template method

`ValidationHandler.handle` always calls `check` and then the next handler. That skeleton is a template method. The handlers linked in `OrderBeans` are the chain: `CustomerValidator`, `CurrencyValidator`, `LineItemsValidator`, `PaymentValidator`. The chain stops at the first failure. Structural rules (a line must have a price, the total must add up) stay in the builder. Policy that can change without changing the aggregate (SKU shape, token required for cards, maximum 20 lines) stays in the chain.

**Follow-up: why not Bean Validation annotations?**
Annotations would work for the field shapes. The chain is there so the order of checks and the "stop at the first" rule are code you can read, and so a unit test can link the same objects without starting Spring. `ValidationChainTest` does that.

## Resilience

`ResilientExecutor` (`order-service/src/main/java/com/orderflow/order/infrastructure/grpc/ResilientExecutor.java`) wraps the gRPC call. Retry is the outer decorator. Each attempt has a time limiter. The circuit breaker wraps the attempt, so a timeout counts as a failure and a success closes the window. Configuration is the `resilience4j` block in the order service `application.yml`: 3 attempts, 150 ms apart, 2 second timeout, circuit opens after 10 calls in a window of 20 when half of them fail, and it stays open for 10 seconds.

`InventoryGrpcAdapter` translates a business status into a `Rejected` result *inside* the supplier. Those results are not exceptions the breaker records. `ResilientExecutorTest` covers a retry that then succeeds, a timeout, and a circuit that opens.

If the breaker is open or the call times out, `PlaceOrderService` returns the order still in `PLACED` with HTTP 202. The recovery job retries. The client is not told the order failed when the failure was ours.

**Follow-up: why is retry outside the breaker?**
Each attempt should count. If the breaker wrapped the whole retry, three timeouts would look like one failure and the breaker would open too slowly. If retry were inside, an open breaker would be retried, which is wasted work.

**Follow-up: what about the Kafka side?**
Listeners use a dead-letter publisher after a few attempts (`OrderBeans` in the order service). A `PermanentMessageException` (payload that will never parse) is not retried. A poison message should not pin a partition. The cost is that the dead-letter topic needs a person or a tool. Nothing in this demo drains it automatically.

## Correlation, metrics, and logs

`X-Correlation-Id` is accepted or minted by `Correlation.resolve`. Servlet services use `CorrelationIdFilter`. The gateway cannot use that filter: it is WebFlux, and a gateway `GlobalFilter` does not run for actuator. `CorrelationGatewayFilter` is a `WebFilter`, so health checks get the header too. gRPC client and server interceptors copy the same value, and the Kafka producer puts it on the record header. The log pattern prints `%X{correlationId}`.

Actuator exposes `health`, `info`, `prometheus`, and `metrics`. Prometheus is in `docker/prometheus/prometheus.yml`.

## How the tests are shaped

Unit tests do not start Docker or Spring. `OrderLifecycleTest`, `ValidationChainTest`, `PaymentStrategyTest`, `PlaceOrderServiceTest`, `PaymentResultHandlerTest`, and `ResilientExecutorTest` are examples. Mockito stands in for ports. AssertJ states the outcome.

Integration tests use Testcontainers:

- `InventoryReservationIntegrationTest` is Postgres plus the real gRPC server. It checks idempotent reserve, release, insufficient stock, and an unknown SKU.
- `OrderOutboxIntegrationTest` is Postgres plus Kafka, with a fake inventory port, and reads `order.events`.
- `PaymentProcessorIntegrationTest` produces `ORDER_PAYMENT_REQUESTED` and expects one declined payment even though the record is sent twice.
- `QueryProjectionIntegrationTest` produces an old snapshot and a new one and reads GraphQL.

`orderflow-e2e` does not put the four applications on one classpath. Their `application.yml` files and Flyway histories would collide. `OrderSagaEndToEndTest` starts the four executable jars as processes against Testcontainers Postgres, Kafka, and MongoDB, places a card that approves and a card that declines, and checks stock and GraphQL.

**Follow-up: why is the end-to-end test a process test?**
Because the bug you care about is "these programs, with separate classpaths, actually complete a saga." An in-process test that calls four services as libraries would pass while the packaged apps still failed to boot.

## What changes at Apple scale

The boundaries can stay. The mechanisms change.

- **Outbox.** Replace the poller with a log tail so publish latency is not a `SELECT` interval, and shard the publisher. Keep the at-least-once contract.
- **Events.** Put the payload in a schema registry (Protobuf, which this repo already uses for gRPC) and stop putting a payment token in the event. Pass a reference into a tokenizer. Encrypt nothing you can avoid storing.
- **Saga.** The coordinator becomes its own deployable, or a workflow engine, with an explicit refund step and a human queue for the dead-letter topic. Timeouts move from a fixed 10 minutes to a per-method SLO.
- **Data.** Orders and inventory get their own primary, replicas for the read-your-write path that can tolerate it, and a partition key that matches the Kafka key. The MongoDB collection is a projection you can rebuild from the log, so it is a cache with a source of truth, not a second source of truth.
- **Inventory.** Sorted row locks do not survive a catalog that is updated millions of times a second. You move to a reservation ledger partitioned by SKU, and you accept a short hold with an expiry instead of a lock across a payment.
- **Resilience.** Timeouts and circuit breakers stay. You add bulkheads so inventory latency cannot eat the whole order-service thread pool, and you page on the breaker-open metric. Virtual threads, which this app enables, remove some thread-pool pain and do not remove the need for a deadline.
- **Gateway.** Rate limits, mTLS, and a mesh replace a single Spring Cloud Gateway process. Correlation ids become trace ids in OpenTelemetry so one order can be followed across the reserve call and both consumers.
- **Idempotency keys.** They get a TTL and a dedicated store. The hash stays. The unique constraint stays.
- **Tests.** The unit and contract tests stay in the inner loop. The process-level saga stays as a pipeline test against containers. A load test measures the place-order path separately from the saga completion path, and you do not quote one number as the other.

The design in this repo is the small version of those choices: explicit ownership, an outbox, a saga that can say what it does not do, and tests that run the real databases.
